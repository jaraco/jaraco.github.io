01
Maintainer problems

Repetition, forever

Repetitive maintenance of shared concerns that are ancillary to the product — in every repository, again next year.

Test methodology Minting releases Metadata Licensing Python versions Ecosystem drift
  • Checkouts aren’t importableThe repo’s shape isn’t the installed shape, so a tooling step must intervene.
  • Backends can’t have dependenciesA PEP 517 backend is installed before anything it would depend on.

Neither is a matter of effort. Both are shapes the ecosystem settled on.

02
Triumph · the whole boilerplate

Three lines, plus a hook

pyproject.toml
[build-system]
requires = ['coherent.build']
build-backend = 'coherent.build'
.github/workflows/main.yml
name: tests
on: [push, pull_request]  # trimmed
jobs:
  main:
    uses: coherent-oss/system/
      .github/workflows/main.yml@main

Name, version, author, description, supported Pythons, licence text, dependencies — all discovered. In use for encutils and tempora, with coh driving build, test and release.

03
Triumph · the essential layout

The root is the package

tempora — the whole repository
tempora/
  __init__.py
  schedule.py  timing.py  utc.py
  tests/
  (meta)/
  pyproject.toml

Clone it into site-packages and import it. No src/, no name spelled twice, no transform between the checkout and the runtime. (meta) keeps the ancillary concerns out of the root.

And the sdist compiles down to flit — every dynamic decision resolved once, so what ships is a static, ordinary project.

Nothing downstream installs this backend, which is how the bootstrap problem stops mattering.

04
Triumph · inference

Derived, not declared

__init__.py — the whole declaration
import sys
import requests

print(requests.get(sys.argv[1]).text)

Dependencies, from the imports. There is no step two.

python/cpython — nobody wrote this
branches still maintained:
  3.11  3.12  3.13  3.14  main
  ^ the oldest one wins

Requires-Python: >= 3.11

Supported Pythons, from CPython itself. A version sunsets, the branch goes, the floor rises.

  • A name database maps imports to distributions — drop the last import and the dependency goes with it
  • Dynamic imports, subprocess calls and version constraints still need an explicit __requires__

05
Challenges

A system of one

  • There’s still boilerplateA workflow definition per repository, and a pyproject.toml to find the backend.
  • Only coherent tooling reads (meta)Every other tool looks in the root, or doesn’t look.
  • flit can’t build extension modulesCompiling down to flit caps the system at pure Python.
  • Tooling expects flat or src layoutNeither shape fits, so type checkers guess the import root wrong.
  • Docs need a service, not a templateSphinx and Read the Docs each want boilerplate in every repository.

The last two are the price of the two answers on the previous plate. A system of one is still a system with an ecosystem around it.

06
In summary

The root holds the code.
The rest is tooling’s problem.

That part is real and running. What’s left is the distance between a system and an ecosystem that knows about it.

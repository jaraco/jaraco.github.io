1997 · the original idea

One job:
also look here

A path configuration file says nothing about names. It extends the search path and lets the finders sort it out.

“New site.py semantics” — 29 Aug 1997

site-packages/mylib.pth
/home/jaraco/code/mylib
/opt/vendor/py

Two lines, two directories on sys.path. Everything inside them becomes importable — whether you meant it or not.

2001 · the escape hatch

“Support import lines in pth files”Patch #103134, 11 January 2001. Twenty-five years of cleverness followed.

zope-nspkg.pth — abridged, and all on one line
import sys, types, os;
p = os.path.join(sys._getframe(1).f_locals['sitedir'], *('zope',));
m = sys.modules.setdefault('zope', ...PathFinder.find_spec(...));
mp = (m or []) and m.__dict__.setdefault('__path__', []);
(p not in mp) and mp.append(p)

It reaches into the caller's frame for sitedir. That detail outlived the people who wrote it — and broke in 3.15.

07
PEP 829 · the hatch closes

The clever line
goes away

Import lines in .pth files are deprecated. Startup entry points move to .start files, which run code on purpose rather than by accident.

Lib/site.py
# - <name>.pth files extend sys.path with
#   additional directories (one per line).
#   Lines starting with "import" are
#   deprecated (see PEP 829).

So the question is no longer whether setuptools should stop doing this. It is what it should do instead.

The whole proposal

The name N
lives at P.

Small. Static. Declarative. Written once, read by everyone.

11
The proposition

Five things it has to do

Readable

  • Static. No code runs to learn the mapping.
  • Inherited. Redirect a package, get its submodules.
  • Reversible. Name to path, and path to name.

Real

  • Honoured by the import system itself — not metadata describing a hack implemented elsewhere.
  • Introspectable at run time, so tracebacks and debuggers can explain what happened.

Get the fourth one right and proxy modules and finder-installing .pth lines stop existing. The runtime and the static view cannot disagree.

12
Why not just extend the path

Two layouts a path entry
cannot express

one name, or everything beside it
# mylib.pth
/home/jaraco/code/mylib/src

# now importable, like it or not:
mylib  scratch  conftest  vendor  setup

Declaring one name should not expose its siblings.

the directory is not the name
~/code/zope.interface/
  __init__.py
  _zope_interface.py

# imported as:  zope.interface
# there is no  zope/  anywhere

The repo is the package. No path entry can say this.

The half nobody has

Ask it backwardsGiven this file, what name is it imported under? Today: a guess, derived from directory structure.

Type checkers, linters, test collectors, coverage, tracebacks, “go to definition”. All of them ask this question. None of them can resolve deterministically.

15
Decision one

Where does the declaration live?

In the .dist-info

  • Owned by the distribution; uninstalls with it.
  • Versioned with the wheel; the obvious home for packaging facts.
  • Every interpreter start must scan every *.dist-info to find out.

In site-packages

  • One readdir — the cost .pth already pays.
  • What names the file, when the redirect is for zope.interface?
  • How does a finder consult it for submodules and subpackages without reading everything?

Startup time is a tradeoff; scanning all metadata directories can be expensive.

16
Decision two

One file,
one syntax

redirects
"coherent.build" = "~/code/coherent.build"
"mylib"          = "~/code/mylib/src/mylib"

TOML, JSON, or one redirect per line, as .pth does. Alongside .start, as PEP 829 did.

And then the hard part

  • Precedence against sys.path entries, and against other redirects.
  • Relative paths — relative to what?
  • May a redirect target be redirected? Do we detect cycles?
  • Filesystem only, or anything an importer can reach?
